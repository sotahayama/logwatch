# logwatch

Mac のシステムログを集め、平常時のパターンから外れた動きを検知する仕組み。

```
agent (Swift) ──1分ごとの件数──▶ server (Next.js) ──▶ PostgreSQL ◀── detector (Python)
                                     │                               15分ごとに学習し直し、
                                     ├─▶ 受信時に統計的な異常検知      毎分 PCA で判定
                                     └─▶ ダッシュボード(30秒ごとに自動更新、検知方法を切り替えられる)
```

## 異常検知(統計的な方法)

「プロセス × 重要度」ごとに、直前60分(エージェントが動いていた分だけ)の件数の中央値とばらつき(MAD)を平常時とし、今の1分がどれだけ外れたかで判定する。

- **急増**:エラー・障害レベルの件数が、平常時のばらつきの6倍以上かつ20件以上増えた
- **沈黙**:平常時に毎分30件以上出すプロセスが0件になった(端末全体が静かな分は除く)

最初は全レベルを対象にしていたが、実データでは「放置→作業開始」だけで30分に約1,400件のアラートが出て、その9割以上が情報・通知レベルだった。使い方で平常時そのものが変わるため、急増はエラー・障害に絞った(約85件に減少)。平常時の変化に追従するのは統計的な方法の限界で、次の機械学習で扱う。

## 異常検知(機械学習:主成分分析)

各分を「(プロセス, 重要度) ごとの件数」を並べたベクトルとみなす。作業開始やスリープでは多くのプロセスが一斉に増減するので、それを少数の主成分(正常部分空間)として学習し、主成分で説明できない残り(残差)が大きい系列を異常とする。システムログの件数に PCA を使う考え方は Xu et al., "Detecting Large-Scale System Problems by Mining Console Logs" (SOSP 2009) と同じ。

- 件数は `log(1+x)` に変換し、系列ごとに標準化してから主成分を求める
- 主成分は3個。残差のばらつきは、学習に使っていない時間帯のデータで見積もる(学習データで見積もると小さく出すぎて誤報が増える)
- 急増はエラー・障害レベルだけ知らせる。学習していない系列(新しいプロセスなど)は、エラー・障害が1分に100件以上のときだけ知らせる
- 画面の「平常時」には、端末全体の状態から予想される件数を表示する

### 評価

実データ(学習161分・評価69分)の評価用の分に既知の異常を12個ずつ混ぜ、10回くり返した平均。PCA は評価期間を15分ずつ進めながら、その時点までのデータで学習し直す(本番と同じ)。通知は、同じ系列で5分以内に続いたアラートを1件にまとめて数える。

| 方法 | 検出率 | エラー急増 | ログ量急増 | 沈黙 | 元データでの通知/時 |
|---|---|---|---|---|---|
| 統計的な方法 | 12% | 30% | 0% | 5% | 13.0 |
| **PCA(本番設定)** | **35%** | **70%** | **0%** | **35%** | **7.0** |
| PCA(情報・通知レベルも対象) | 38% | 70% | 10% | 35% | 20.0 |

再現するには `cd detector && .venv/bin/python -m logwatch_detector.evaluate`。

評価から分かったこと:

- 最初の評価では PCA の通知が1時間に146件と多すぎた。原因は (1) 学習データに合わせすぎて残差のばらつきを小さく見積もっていたこと、(2) 一度学習したきりで新しい平常に追従していなかったこと、(3) 同じ現象を毎分数えていたこと。それぞれ交差検証・定期的な学習し直し・通知のまとめで対処した
- 主成分が多すぎると、個々の系列の動き(=異常)まで主成分が吸収してしまう。主成分の数を分散の割合で自動に決める方式も同程度の成績だったが、差が誤差の範囲だったため少なく固定した
- 1つのプロセスのログ量だけが5倍になる異常は、どちらの方法でもほとんど見つけられない(今後の課題)
- データがまだ約4時間ぶんと少ないため、数値は暫定。データがたまったら測り直す

## 設計方針

- **ログ本文は送らない**:個人情報を含みうるため、エージェントは本文を読み出さず、「1分 × プロセス × 重要度 の件数」だけを送る
- **取りこぼさない**:エージェントはどこまで送ったかをチェックポイントに記録し、送信に成功したときだけ進める。止まっていた場合は再起動時に続きから送る(最大1時間遡る)
- **何度届いても同じ結果**:サーバーは同じ (端末, 分, プロセス, 重要度) を足し込まず置き換えで保存するので、再送で件数が水増しされない
- **トークンは平文で持たない**:サーバーにはハッシュだけを保存する。エージェントには環境変数で渡し、コマンド引数(他のユーザーから見える)には出さない

## 構成

| ディレクトリ | 内容 |
|---|---|
| `agent/` | 収集エージェント(Swift、OSLogStore)。管理者ユーザーで実行する |
| `server/` | 受信API・統計的な検知・ダッシュボード(Next.js 16 + Prisma + PostgreSQL) |
| `detector/` | PCA による検知のワーカーと評価(Python + scikit-learn) |

## 動かし方

PostgreSQL を用意する。

```bash
brew install postgresql@18
brew services start postgresql@18
createdb logwatch
createdb logwatch_test
```

サーバーを起動し、端末を登録する(表示されたトークンを控える)。

```bash
cd server
npm install
echo "DATABASE_URL=\"postgresql://$USER@localhost:5432/logwatch\"" > .env
npx prisma migrate dev
npm run dev
npm run host:add -- my-mac
```

エージェントを動かす。

```bash
cd agent
swift build -c release
LOGWATCH_TOKEN=<控えたトークン> .build/release/logwatch-agent --endpoint http://localhost:3000/api/ingest
```

`--endpoint` を省略すると、集計結果を標準出力に NDJSON で書き出す。初回だけ過去のログを取り込むなら `--backfill <分>` を付ける。

PCA のワーカーを動かす。

```bash
cd detector
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m logwatch_detector.worker
```

## 常駐させる(launchd)

サーバー・エージェント・PCA ワーカーを、ログイン時に自動で起動し、落ちたら再起動するよう登録する。PostgreSQL は `brew services` で常駐させておく。

```bash
LOGWATCH_TOKEN=<端末のトークン> scripts/launchd.sh install
scripts/launchd.sh status
scripts/launchd.sh uninstall
```

- ダッシュボードは http://127.0.0.1:3001 。認証がないため、同じネットワークの他の端末からは見えないよう `127.0.0.1` だけで待ち受ける
- 設定ファイルは `~/Library/LaunchAgents/com.logwatch.*.plist`。エージェントのトークンを含むので本人だけが読める権限(600)で作る
- ログは `~/Library/Logs/logwatch/`
